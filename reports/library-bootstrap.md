## 1. What the loader actually expects (derived from `src/app/commands/elec.rs`)

### 1.1 `ELECLIB <folder>` — `elec.rs:1614`

1. The argument is taken **bare** (trimmed, not unquoted), so a path with spaces cannot be used.
2. It lists only `*.dxf` **directly in that folder** (`read_dir`, no recursion, `elec.rs:1622-1634`),
   sorted by path. That is why the starter set lives in `library/starter/` and is a separate
   `ELECLIB` target, not merged into `library/`.
3. **The file stem is the block name** (`elec.rs:1641-1649`). `CONT-NO.dxf` becomes block
   `CONT-NO`; the DXF's own `BLOCK` name inside the file is irrelevant.
4. A file whose stem is already a block in the drawing is skipped (`already in this drawing`).
5. Geometry source: `document.entities()` — and that call returns **every** entity, block
   definitions included. The "take it from the first non-`*` block" fallback at `elec.rs:1657-1677`
   is therefore only reachable for a file with no entities at all. Measured consequence in §5.9:
   block-based symbol files **do** load (contradicting `reports/code-audit.md`).
6. The block is defined with **base point `(0,0,0)`** (`define_block_from_owned_entities(...,
   DVec3::ZERO)`, `elec.rs:1711-1715`), so symbol geometry must already be relative to the
   insertion origin. The real symbol blocks all have base `(0,0,0)`; the harvester still bakes the
   base offset in case a file has another one.
7. **Attribute definitions**: if the file already contains `ATTDEF` entities, the loader keeps them
   (`already_defined`, `elec.rs:1691-1694`). Only when it finds none does it fabricate one per
   `library.tsv` tag, at a **fixed height 2.0 and `y = 4.0 - row*2.5`** (`elec.rs:1694-1709`) —
   symbol units, not the drawing's text size. Both libraries therefore embed real `ATTDEF`s
   (except the deliberate `fabricated_batch.txt` probe, which measures the fabricated output).
8. **Label height** is measured from the loaded geometry: `span / 8`, where span is the largest
   bbox dimension of `LINE`/`CIRCLE`/`ARC`/`LWPOLYLINE` only (`elec.rs:1735-1760`). It is used by
   `ELECPLACE` for the placed attribute text and by `ELECSETATTR` for attributes it has to add.
   `TEXT`, `SPLINE` and `SOLID` do not contribute to the measured span.
9. `WD_M` is skipped wherever a block insert becomes a component (`is_setup_block`,
   `elec.rs:4332`); the harvested library must not (and does not) contain `WD_M.dxf`.

### 1.2 `library.tsv` — `read_library_manifest`, `elec.rs:115-161`

Tab-separated, **line 0 is skipped** (a header), blank lines are skipped.

| column | meaning | evidence |
|---|---|---|
| 1 `symbol` | symbol name; matched case-insensitively against the block name | `elec.rs:132,144-146` |
| 2 `class` | device class, fed to `elec::default_prefix` for the tag prefix; the palette groups by it | `elec.rs:133,1868-1876` |
| 3 `attributes` | `\|`-separated attribute tags; the template `ELECPLACE`/`ELECINSERT` create | `elec.rs:134,151-153` |
| 4 `scale` | uniform insert scale; **`ELECPLACE` only** (`elec.rs:1918-1932`), parsed as `f64 > 0`, default 1 | `elec.rs:136-140` |

That is the 4-column format `ELECMAKESYMBOL` itself appends (`elec.rs:2349`). `STATUS.md` §6
describes a **5-column** historical file (`symbol, class, attributes, sheets, scale`); the loader has
no column for `sheets`, so it reads column 4 as the scale. Proven in §5.3.

### 1.3 Class → IEC tag prefix (`crates/elec/src/numbering.rs:259-304`)

`default_prefix` matches the class's **lowercased prefix**: `contactor|relay|timer|overload` → `-K`,
`motor`→`-M`, `terminal`→`-X`, `fuse`→`-F`, `circuit breaker|breaker`→`-Q`,
`button|switch|selector`→`-S`, `sensor|prox`→`-B`, `plc`→`-P`, `power supply`→`-G`,
`drive|soft starter`→`-U`, `transformer`→`-T`, `cable`→`-W`, `solenoid|valve`→`-Y`,
`lamp|indicator`→`-H`, otherwise **the first alphabetic character of the class**. A class whose name
does not begin with one of those words silently gets a prefix from its first letter — which is why
`library/`'s classes were chosen so the prefixes are unique (§2.2).

### 1.4 Palette preview — `elec_symbol_segments`, `elec.rs:2379-2450`

Segments come from the block's own entities: `LINE` = 1, `CIRCLE` = 16, `ARC` = 8,
`LWPOLYLINE` = vertices − 1, everything else 0. There is a hard **`MAX_SEGMENTS = 400`** cap that
skips whole entities once 400 have been produced (`elec.rs:2380,2395`); `FAN` hits it (428 → 410
segments reported). If the block lookup fails, the symbol previews empty and `label_height` falls
back to 0.125 without any error.

### 1.5 Units: what the code assumes vs what the real drawings are

Measured from the 34 sheets:

* A whole A3 sheet is **35.5 drawing units wide × ~25.1 tall** (maximum extent of model-space
  geometry; `ELECSHEET A3` on `FC1000495-002` fitted a 40.82 × 28.87-unit frame at `1:10`, i.e. it
  divided 35.5/25.1 by 1.15). If this were millimetres, A3 would be 420 × 297.
* One device symbol is **0.06–1.25 units** (CONT-NO 0.875 × 0.25; TERMINAL 0.125; Ground 0.375 tall;
  ELCB 0.625 × 0.8125; FAN 1.25 after its 0.125 insert scale).
* The dominant model-space text height is **0.125** (3653 entities), then 0.15 (2135); 0.25 only 75.

So the drawings are drawn at roughly **1 unit ≈ 11.8 mm on paper**, and the old code comments agree
("their text is 0.125 tall against symbols under a unit", `elec.rs:1752`). But the drafting aids are
tuned for a **millimetre-scale** drawing: `DOT_RADIUS = 1.0` (`:2101`), wire-number `LABEL_HEIGHT =
2.5` (`:663`), cross-reference `LABEL_HEIGHT = 2.0` (`:1158`), `ELECINSERT`'s auto-advance
`rightmost + 40.0` (`:1438`), and `ELECSHEET`'s A3 = 420 × 297 (`:3825`). Concretely, on a real
sheet `ELECJUNCTIONS` would draw a dot 1.6× the height of a contact symbol and `ELECWIRENUMBER`
would set text 20× the project text height; `ELECINSERT` puts the next device more than a sheet
width away. **This is the first thing to fix (§6.1).**

Notes and judgement calls, all visible in `library/harvest_report.tsv`:

* The **attribute tag sets are not invented**: the sheets' attribute-carrying blocks
  (`HDV1TFL`, `HMS21`, `HCR21`, `HMO13`, `HPX11`, `HSV1`, `HLT1G`, `HA1S1`, `HMS1`, `HCR1`,
  `HT0_01/02`) use exactly this ACADE vocabulary — `TAG1`/`TAG2`, `FAMILY`, `CAT`, `MFG`,
  `DESC1..3`, `LOC`, `INST`, `XREF`, `XREFNC`/`XREFNO`, `TERM01..04`, `X1TERM..`, `RATING1..4`,
  `WDTAGALT`, `ASSYCODE`.
* **Case-colliding block names were merged** (the app's block table is case-insensitive, and the
  filesystem is too, so `TERMINAL.dxf` and `terminal.dxf` cannot coexist). Measured: `TERMINAL`
  (101 inserts)/`terminal` (10), `Ground` (52)/`GROUND` (4), `PLUG` (8)/`Plug` (16),
  `PB-NO` (6)/`Pb-no` (5), `Arrow-l` (3)/`ARROW-L` (3), `PL`/`Pl` — each pair has **identical
  geometry**, so merging is lossless here. The harvester records which casing it kept as
  `source_block`.
* **`TY` and `PT` are ambiguous from geometry alone.** `TY` is four concentric circles and sits
  next to device-description text, so it is classed "Device Marker" (`-D`); `PT` is a small circle
  with a diagonal and appears beside wire names `L1`/`N`/`GND`, so it is classed "Connection Point"
  (`-C`). Rename them in `library/library.tsv` if the client calls them something else — only the
  class (=> tag prefix) and the palette grouping depend on it.
* Classes were picked so that **all 14 tag prefixes are unique** in this library; otherwise
  `ELECNUMBER` would number two unrelated device families in one sequence (it groups by prefix,
  `elec.rs:377-401`). `BOX` is "Graphic Box" only for that reason — it is not a device.

## 3. The proof (`tests/ecad/run_smoke.py`)

```
$ py -3.13 tests/ecad/run_smoke.py
...
======================================================================
99/99 checks passed
```

What it does, in order, all with `--each <batch> <drawing.dxf>` on a temp drawing:

1. **Starter drafting path** — `ELECNEW`, `ELECLIB library\starter`, six placements, three
   `ELECSETATTR`, `ELECLIST`, `ELECBOM`, two `ELECWIRE` runs, `ELECJUNCTIONS`, `ELECNUMBER`, `QSAVE`.
   Then it re-reads the saved DXF and checks tags, attribute values and heights, layers, exact wire
   coordinates, the junction dot, and that every one of the 27 blocks has exactly the geometry and
   `ATTDEF` count of its source file.
2. **Round trip** — the saved drawing is re-opened and re-saved by the app (`--export`); insert
   points, tags, attribute values and block origins must be identical.
3. **`ELECMAKESYMBOL`** — draw a rectangle, `SELECTALL`, author `SMOKE_SYM`; the DXF and the
   manifest row are checked, then the library is reloaded (28 symbols) and the new symbol placed.
4. **Loader edge cases** — the 5-vs-4-column manifest (§5.3), block-only symbol files (§5.9),
   mixed model-space+block files (§5.10), empty DXF, unknown block (§5.8).
5. **The fabricated-attribute branch** — a symbol with no ATTDEFs, to measure what `ELECLIB`
   synthesises (§5.6).
6. **The harvested client library** — `ELECLIB library\`, 18 placements with the rebuilt binary,
   geometry/kinds/ATTDEF counts, the real 0.875 × 0.25 CONT-NO geometry, FAN's baked 0.125 scale,
   the inlined Arrow-l SOLID inside 24VDCPRX, the 18 tag prefixes, the 0.125 text height, and that
   `WD_M` is not a symbol.
7. **The real sheets** (§4).
8. **The machine-readable files** — the profile and harvest report are parsed back and checked.

## 5. Where the code's expectations were broken or surprising

Each item is measured, not inferred. This section is the useful part.

### 5.1 The whole command layer is tuned for a different unit scale than the real drawings

Code constants assume a millimetre drawing (A3 = 420 × 297, dot radius 1 unit, text 2.0–2.5 units,
next-symbol step 40 units). The client's sheets are **35.5 × 25.1 units per A3**, device symbols
0.06–1.25 units, text 0.125. Consequences on real data: `ELECJUNCTIONS` dots are ~1.6× a contact
symbol tall; `ELECWIRENUMBER`/`ELECXREFWRITE` text is 16–20× the drawing's text; `ELECINSERT`
auto-advance is wider than the sheet. `ELECSHEET` alone compensates (it fits the frame to content).
This is why the old `library.tsv` had a `scale` column: harvested symbols were sub-unit and had to be
scaled up for the mm-tuned aids — but see 5.3, `ELECINSERT` never applies it.

### 5.2 The real sheets carry no symbol attributes, so the extractor sees (almost) nothing

`components_of` requires `insert.attributes` to be non-empty (`elec.rs:196`). On the client sheets
only `WD_M` and 12 module blocks have attributes; `WD_M` is then excluded. Result: **0 components on
30/34 sheets**, 4 components on the best sheet. Every downstream command (`ELECLIST`, `ELECBOM`,
`ELECNUMBER`, `ELECWIRELIST` anchors, `ELECTERMINALS`, `ELECTSIDES`, `ELECXREF`, `ELECPANEL`) is
blind. The tag text exists, but as plain `TEXT`, which nothing reads as device data.

### 5.3 The `library.tsv` scale column: 5-column manifests are mis-parsed, and `ELECINSERT` ignores it

`read_library_manifest` reads column 4 as `scale` and ignores anything after it. The historical
format in `STATUS.md` §6 is `symbol, class, attributes, sheets, scale`, so column 4 is the **sheet
count**:

```
# library with a 5-column row: FUSE<TAB>Fuse<TAB>TAG1|...<TAB>12<TAB>2   (sheets=12, scale=2)
ELECLIB: loaded 1 symbol(s) ... 1 in the catalogue, 7 preview segment(s).
ELECINSERT: placed FUSE as -F1 at 0.00,0.00.
ELECPLACE FUSE  Specify insertion point:
=> (x, insert scale) from the saved DXF: [(0.0, 1.0), (60.0, 12.0)]
```

`ELECPLACE` inserted at **12.0** (the sheets column) and the real scale (2) was never read. With a
4-column manifest (`…<TAB>2`), `ELECPLACE` correctly inserts at 2.0 — and `ELECINSERT` still inserts
at 1.0, because `elec_insert` never reads `entry.scale` (`elec.rs:1498-1520` uses only
`label_height`). **Two insertion paths disagree about symbol size.**

### 5.4 `ELECPLACE` throws away the symbol's own attribute positions

`PlaceSymbolCommand::build` stacks attributes at `insert.y - height - row*1.25*height` (`place.rs:54-62`),
ignoring the block's `ATTDEF`s. Measured in the same drawing: `ELECINSERT` honours the definitions
(7/7 attributes at their defined offsets), `ELECPLACE` is off by up to 0.125 units (= one text
height) on a 1-unit symbol — the tag text lands inside the symbol instead of below it. On the
client's sub-unit symbols the error is a whole symbol height. `ELECPLACE` also only fills `TAG1`;
the other attributes come in blank even when the block defines defaults.

### 5.5 A symbol has exactly one anchor: its insertion point

`elec_collect` turns each attributed insert into one `Anchor` at the insert point
(`elec.rs:875-891`), and the netlist only joins an anchor when its point coincides with a wire
endpoint. Real ACADE symbols keep their pins **inside** the block (`ELECPLC` even stores pin
coordinates in `X1TERMnn` attributes for exactly this reason), so no real wire ever reaches an
anchor: `ELECWIRELIST` reports 0 nets on both sheets. Pin-level connectivity is a design gap, not a
data gap; no library can fix it.

### 5.6 The fabricated-attribute fallback is unusable at real symbol sizes

For a symbol file with no `ATTDEF`s, `ELECLIB` fabricates definitions at **height 2.0** and
`y = 4.0 - row*2.5`, in symbol units (`elec.rs:1696-1709`). Measured on a 0.875 × 0.25 contact:

```
fabricated ATTDEF heights=[2.0, 2.0] ys=[4.0, 1.5]   (ELECLIB would measure span/8 = 0.031 for it)
```

i.e. the "Tag" text would be 8× the symbol's height and start 4 units above a symbol that is
0.25 tall. Both delivered libraries avoid this by embedding `ATTDEF`s, but `ELECLIB`'s fallback —
the path every harvested library takes — is broken for exactly the symbols this project has. The
`label_height` measurement has the mirror-image problem: `span/8` is 0.0156 for a 0.125-unit
terminal, while the project's text is 0.125, so `ELECSETATTR` on a harvested symbol would add text
8× too small. It needs a floor at the drawing's text height (or WD_M `FEATURE_SCL`/`UNIT_SCL`).

### 5.7 `ELECBOM`/`ELECLIST` report the block name as the class

`components_of` builds `Component::new(id, &insert.block_name, "")` (`elec.rs:200`), so the
"Class name" column and the BOM grouping key are the **symbol/block name**, not the `class` column
of `library.tsv`. Proven on real data: BOM rows start with `HMS21` and `HMO13`. The manifest's class
only reaches the tag prefix (`ELECPLACE`/`ELECINSERT`/`ELECNUMBER`). It also means identical parts
in different symbols never fold into one BOM row, and a renamed symbol renames its BOM class.

### 5.8 `ELECPLACE` writes a dangling INSERT; `ELECINSERT` then accepts it as a template

`ELECPLACE NOSUCH` + a point creates `INSERT NOSUCH` even though no block exists (the palette can
only list real symbols, but a stale manifest row or a typo reaches this). `ELECINSERT` normally
refuses an unknown block with a clear message — **but if a dangling insert of that name already
exists, it clones it and succeeds** (the template path at `elec.rs:1450-1466` bypasses the
block-exists check). A drawing with the dangling insert still loads and saves cleanly, so nothing
complains later. The `#6` "Fix the loader" item in the old audit should be: validate the block on
both paths.

### 5.9 Block-only symbol files **do** load (the audit's "loader bug" is stale)

`reports/code-audit.md` §"two loader bugs" claims symbols with geometry inside a `BLOCK` definition
yield `no geometry`, because the fallback uses `block_entity_handle` instead of the record handle.
Measured against the built binary: a block-only `BOXSYM.dxf` loads
(`ELECLIB: loaded 1 symbol(s) … 6 preview segment(s)`), becomes a 6-`LINE` + 2-`ATTDEF` block, and
inserts. The fallback is simply unreachable: `Document::entities()` returns block-definition
geometry too (its own doc comment says so), so `entities.is_empty()` is false. The `block_entity_handle`
bug is real only for a file with zero entities — which then reports "no geometry" anyway.

### 5.10 A symbol file with geometry in *both* places silently merges them

Because `entities()` returns everything, a file with one model-space line **and** a block definition
produces a symbol containing all of it: `MIXED.dxf` (1 model-space line + 2 lines in block `MIXED`)
became a 3-line symbol. Not a bug for the loader, but a trap for anyone authoring symbols: keep the
geometry in exactly one place (the delivered libraries use model space only).

### 5.11 The palette silently truncates a symbol at 400 segments

`MAX_SEGMENTS = 400` (`elec.rs:2380`) skips whole entities once the count is reached, with no
warning. `FAN` has 428 segments of geometry and previews as 410 — a visibly clipped thumbnail. Only
the palette is affected.

### 5.12 Real block names differ only by case, which this app cannot represent

`TERMINAL`/`terminal`, `Ground`/`GROUND`, `PLUG`/`Plug`, `PB-NO`/`Pb-no`, `Arrow-l`/`ARROW-L`,
`PL`/`Pl`. The app's block table and lookup are case-insensitive (`normalize_name`), and so is the
Windows filesystem, so these merge — measured geometry is identical for every pair, so nothing is
lost today, but a future project where they differ *would* silently lose one. The harvested library
records which casing it kept.

### 5.13 `ELECBOM` writes no file when it finds no rows

`ELECBOM <file.csv>` returns at the "no components" branch before writing (`elec.rs:237-242`), so a
batch that expects a CSV has to distinguish "empty BOM" from "command failed" by absence of a file.
On real data this is the normal case (§4.1).

### 5.14 The ACADE setup block appears twice per sheet

68 model-space `WD_M` inserts on 34 sheets (two identical inserts each, same values). Anything that
counts `WD_M` (e.g. a "component count" report before the `is_setup_block` filter) would
double-count; the filter is correct and should stay.

## 6. Top 3 things to fix in the Rust code

**6.1 Give the drawing a scale and use it for every drafting aid.**
`DOT_RADIUS` (1.0), `ELECWIRENUMBER`/`ELECXREFWRITE` text heights (2.5/2.0), `ELECINSERT`'s
`+40.0` step, `ELECSHEET`'s paper sizes and `ELECLIB`'s `label_height = span/8` all assume a
millimetre drawing; the client's sheets are 35.5 units per A3 with 0.125 text. Read
`FEATURE_SCL`/`UNIT_SCL` from `WD_M` (both are `1.0` on every sheet) or derive the factor from the
content extent, and replace the constants with values scaled by it; clamp `label_height` to at least
a configured text height. Until this is fixed, every command that draws something on a real sheet
draws it 10–20× too big.

**6.2 Decide where component data comes from, then fix `components_of`.**
Today it only accepts attributes on the insert, and the client's symbols have none — so 30/34
sheets produce zero components and `ELECNUMBER` has nothing to number. The two workable routes:
(a) make the library symbols self-describing (done: `library/` symbols embed `ATTDEF`s and
`ELECINSERT` creates the `ATTRIB`s, so newly drafted devices work), and/or (b) teach the extractor to
recover a tag from the adjacent `TEXT`/`ATTRIB` the drawings actually use. While in there, resolve
the class through `library_index` instead of using `block_name` for `Component::class`
(`elec.rs:200`), so `ELECLIST`/`ELECBOM` report `Contactor`/`Terminal` rather than `CONT-NO`/`HMS21`.
Optionally store pin points (ACADE `X*TERM*` attributes, which `ELECPLC` already writes) so the
netlist can attach wires, otherwise `ELECWIRELIST` stays empty on real sheets.

**6.3 Make `library.tsv` parsing match the file the project actually has, and make both insertion
paths agree.**
(i) Accept the historical 5-column manifest (`symbol, class, attributes, sheets, scale`) — currently
`sheets` is read as `scale` and a real scale of 2 inserts at 12 (proven). (ii) `ELECINSERT` must apply
`entry.scale` like `ELECPLACE` does; today a scaled library inserts at 1:1 through one command and
scaled through the other. (iii) `ELECPLACE` should clone the block's `ATTDEF` positions (as
`ELECINSERT` does) instead of re-stacking text at the insertion point. Small, contained changes —
and they are what makes a harvested library behave the same whichever command placed it.

*Secondary, cheap:* validate the block in `ELECPLACE` and in `ELECINSERT`'s template path (5.8); raise
or remove the palette's 400-segment cap for small symbols (5.11); measure `label_height` from
`CIRCLE`/`ARC` bounding boxes rather than sampled segments, and give it a floor (5.6).
